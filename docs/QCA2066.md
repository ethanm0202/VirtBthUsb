# QCA2066 bring-up

How DeckBtUsb takes the Steam Deck OLED's Bluetooth controller from the stock driver, loads its firmware, and hands it back.

The command set, firmware format and file-selection rules follow the upstream Linux driver: [`drivers/bluetooth/btqca.c`](https://git.kernel.org/pub/scm/linux/kernel/git/torvalds/linux.git/tree/drivers/bluetooth/btqca.c?id=a5218c6474df97f2e7f3af15dcdfc674bae5c137) (`qca_uart_setup`, `qca_read_soc_version`, `qca_tlv_check_data`) and [`hci_qca.c`](https://git.kernel.org/pub/scm/linux/kernel/git/torvalds/linux.git/tree/drivers/bluetooth/hci_qca.c?id=a5218c6474df97f2e7f3af15dcdfc674bae5c137), where ACPI `QCOM2066` maps to `QCA_QCA2066`. Timings and the vendor driver's behaviour come from its own debug log (see [Vendor log](#vendor-log)) and from its INF.

## Identity

Values reported by the controller on the test device:

| Field | Value |
|---|---|
| ACPI | `\_SB.FUR4.QTBT`, hardware IDs `ACPI\VEN_QCOM&DEV_2066`, `ACPI\QCOM2066` |
| UART | `ACPI\AMDI0020` (`amduart.sys`, SerCx2) |
| SoC ID | `0x400C1211` |
| Product ID / ROM patch / build | `0x13` / `0x38E6` / `0x0201` |
| ROM build string | `BTFW.HSP.2.1-00124-ROM-1` |
| Board ID | `0x0309` |

## Serial configuration

| Setting | Value |
|---|---|
| Line | 8N1, RTS/CTS handshake, XON/XOFF limits as the vendor driver sets them |
| Initial rate | 115200 baud |
| Operating rate | 3,000,000 baud. The AMD UART cannot produce 3,200,000 (`IOCTL_SERIAL_SET_BAUD_RATE` returns `STATUS_INVALID_PARAMETER`), which is the rate the shipped NVM files request. |
| Write timeout | 1500 ms total |
| Reads during bring-up | Interval 20 ms: a read pends until the first byte and returns after a 20 ms gap |
| Reads in steady state | Complete on the first byte (interval and multiplier `MAXULONG`, constant 1000 ms), so in-band sleep bytes are seen at once |

## Waking the controller

A sleeping controller holds its RTS, the host's CTS, low. A write sent while CTS is low cannot leave the UART FIFO, and cancelling it may not retire it, which blocks power transitions. Before the first byte, the driver reads the modem status. If CTS is low, it toggles RTS (low 5 ms, high 5 ms, up to five times) until CTS asserts, as the vendor driver does. No byte is sent without observed CTS.

## Bring-up sequence

`src/common/qca_init_fsm.c` drives the sequence. `src/driver/qca_uart.c` performs the I/O.

1. **Reach ROM state.** Send the version request `01 00 FC 01 19`, trying 115200, then 3,000,000, then 3,200,000 baud (a rate the host UART refuses is skipped without sending anything). A controller that answers at 115200 is in ROM. A controller left running firmware by another driver answers at 3,000,000, or stays silent while asleep in in-band sleep. The driver then resets it at the rate it answered on, or at 3,000,000 when silent: in-band wake `0xFD` three times, 10 ms, SoC reset `01 40 FC 00`, 200 ms. The controller must then answer at 115200.
2. **Switch rate.** `0xFC48` with index 14 (3,000,000 baud). No reply is awaited. The host UART follows.
3. **Rampatch.** `hpbtfw21.tlv` (155,044 bytes) in `0xFC00`/`0x1E` segments of up to 243 bytes.
4. **Board ID.** `0xFC00`/`0x23` returns the board ID (`0x0309`).
5. **NVM.** The file is selected from the SoC ID and board ID with the upstream rule. SoC ID `& 0xFF00 == 0x1200` means the GlobalFoundries variant (`g` suffix), and the board ID gives the extension, so `hpnv21g.309`. `hpnv21g.bin` is the fallback. Before sending, the driver overwrites one byte on the wire: `data[1]` of the NVM's HCI tag, the UART rate index, from 17 (3.2 Mbaud) to 14 (3.0 Mbaud). The vendor driver changes exactly this byte and no other in the part of the NVM its log shows. The file itself is not modified.
6. **Logging off.** `0xFC17` with `0x14 0x00`. This controller answers with an 8-byte completion that echoes the sub-op.
7. **Build info.** `0xFC00`/`0x20` reports `BTFW.HSP.2.1.0-00641-VER_PATCHZ-1` after patching.
8. **`HCI_Reset`.** Completion `0E 04 01 03 0C 00`.

On the test device, bring-up from ROM takes about 3.7 s. Bring-up from a controller that first needs the reset takes about 7.3 s.

## Firmware files

Five files from Valve's Windows Bluetooth driver package (`qcbtuart.inf_amd64_*` in the DriverStore) are copied into the driver package by `tools/stage-firmware.ps1` at build time, then installed to `%SystemRoot%\System32\drivers\DeckBtUsb\`:

`hpbtfw21.tlv`, `hpnv21.bin`, `hpnv21g.bin`, `hpnv21.309`, `hpnv21g.309`

They are not part of this repository.

## In-band sleep

With the operating firmware loaded, the controller uses Qualcomm in-band sleep. It sends `0xFE` when it goes to sleep and `0xFD` when it wakes, and expects `0xFC` in reply. It also accepts `0xFD` from the host as a wake request. The driver acknowledges every wake indication and strips the IBS bytes from the HCI stream.

## Handing the controller back

On stop (package removal, disable, or D0 exit), the driver ends the session with the vendor's recovery sequence: IBS wake `0xFD` three times, SoC reset `01 40 FC 00`, 200 ms settle. It then records the rate at which the controller answers (`UartHandbackBaud`, normally 115200). The vendor driver's bring-up starts at 115200 and cannot recover a controller left asleep at the operating rate on its own.

## Sleep

Across S3 the controller loses its firmware and comes back in ROM at 115200. The driver repeats the bring-up at D0 entry and replaces the emulated USB device (see [ARCHITECTURE.md](ARCHITECTURE.md#power)).

## Vendor log

The stock driver `qcbtuart.sys` writes a text log of its bring-up, including every HCI command and event, when these values are set under `HKLM\SYSTEM\CurrentControlSet\Services\QcBluetooth\Parameters` before it loads:

| Value | Effect |
|---|---|
| `BtLogEnabled = 1` | writes `C:\Windows\ServiceState\QcBluetooth\Data\btlog.log` |
| `BtLogAppend = 1` | appends instead of overwriting |
| `BtSnoopHciEnabled = 1` | also writes `btsnoopHCI.log` |

`tools/vendor-log.ps1 -Arm | -Collect | -Disarm` sets, copies and clears them. The log grows quickly (tens of MB per boot).
